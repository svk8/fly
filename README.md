# FlyParcel: Telegram-бот + Mini App

Чат-бот и Mini App — два интерфейса одного сервиса. Пользователи, правила безопасности, блокировки, рейсы, посылки и сделки общие.

```text
Telegram чат → Python / aiogram ─┐
                               ├→ общие сервисы → SQLAlchemy → SQLite
Telegram Mini App → Node → API ─┘
```

Python получает сообщения через long polling и одновременно обслуживает aiohttp API. Node.js раздает React-приложение и передает `/api/*` этому API. Он не получает Telegram updates, не хранит вторую базу и не имеет токена бота в контейнере. Caddy обеспечивает внешний HTTPS. В корне один Dockerfile с целями web и bot и один compose.yaml для запуска всего проекта.

## Поведение

- Рейс или посылка, созданные в чате, видны в Mini App. Созданные в Mini App видны в поиске и разделе «Мои заявки и рейсы» бота.
- Уведомления о подходящих маршрутах и новых откликах приходят через того же бота независимо от места создания заявки.
- Сделка из любого интерфейса видна в `/deals` и разделе сделок Mini App. Владелец объявления подтверждает договоренность, попутчик подтверждает досмотр и прием, отправитель подтверждает доставку.
- Участник не может менять чужую сделку, отменять чужую заявку или откликаться от имени владельца чужого рейса. Повторные отклики запрещены. Отмена заявки с подтвержденной сделкой отклоняется.
- Профиль и согласие на правила едины. /admin, /ban и /unban доступны ADMIN_IDS; блокировка действует в обоих интерфейсах.
- Mini App проверяет Telegram initData на сервере. Просмотр через обычный браузер не дает авторизации. Сессия действует 24 часа; затем приложение нужно переоткрыть.

## Настройка

Старый токен был в исходниках и браузерном коде. Отзовите его в BotFather и получите новый. Удаление из текущего кода не удаляет токен из истории Git или старых сборок.

```bash
cp .env.example .env
```

Задайте один `BOT_TOKEN`, при необходимости `ADMIN_IDS`. Для локального просмотра оставьте `APP_URL` пустым и `DOMAIN=localhost`. Для сервера задайте HTTPS-адрес `APP_URL` и домен `DOMAIN` без `https://`. Для нормальной работы оставьте `BOT_POLLING=true`. Node.js не использует токен. Webhook и `TELEGRAM_WEBHOOK_SECRET` больше не нужны: сообщения получает только Python-бот.

## Локальный просмотр через Docker

Заполните BOT_TOKEN в корневом .env. APP_URL может оставаться пустым: для просмотра сайта домен и сертификат не требуются.

```bash
docker compose up -d --build
```

Откройте http://localhost:3000. Запускаются бот/API и веб-приложение; HTTPS-прокси в локальном режиме выключен. Python, npm и виртуальное окружение на компьютере для этого не нужны. При необходимости смените WEB_PORT в .env, например на 3001.

Бот работает через polling. В браузере можно посмотреть интерфейс; реальные заявки и сделки требуют Telegram-авторизации. Чтобы проверить Mini App полноценно, настройте публичный HTTPS-туннель к localhost:3000, укажите его адрес в APP_URL и пересоздайте бот командой `docker compose up -d bot`. Затем откройте приложение через кнопку бота в Telegram.

## Запуск на VPS

Для небольшого старта: Linux VPS с 2 vCPU, 2–4 ГБ RAM, SSD от 25 ГБ, Docker с Compose, домен и доступ к BotFather. SQLite и polling рассчитаны на один экземпляр Python backend. При масштабировании потребуются PostgreSQL и отдельная стратегия получения Telegram updates.

1. Направьте DNS домена на VPS. Если есть AAAA-запись, IPv6 тоже должен указывать на VPS.
2. Разрешите входящие 80/443, ограничьте SSH. Порт 3000 доступен только на loopback-интерфейсе сервера, порт 8000 не публикуется.
3. Загрузите проект, заполните `.env`, ограничьте права и подготовьте каталог копий:

```bash
chmod 600 .env
mkdir -p backups
sudo chown 1000:1000 backups
docker compose --profile production up -d --build
docker compose ps
docker compose logs --tail=100 bot app proxy
```

Профиль production включает Caddy, который получает и обновляет HTTPS-сертификат. Python автоматически устанавливает кнопку меню бота на APP_URL и команды /start, /profile, /deals, /rules. При старте он удаляет старый webhook, сохраняя ожидающие обновления. Не запускайте другой polling-процесс с тем же токеном.

Проверьте `https://ваш-домен/api/health`, /start и открытие приложения. С двух аккаунтов создайте рейс в чате и посылку в Mini App, проверьте уведомление, отклик и изменение статуса в обоих интерфейсах. После `docker compose restart bot app` опубликованные данные должны сохраниться.

## Локальная разработка

Нужны Python 3.11+ и Node.js 24.x.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r bot/requirements.txt
# Заполните .env
python bot/main.py
```

В другом терминале:

```bash
npm ci
npm run dev
```

Запускайте обе команды из корня проекта. API по умолчанию на `127.0.0.1:8000`, сайт на `localhost:3000`. Для проверки настоящей Mini App используйте HTTPS-туннель к порту 3000, укажите его URL в APP_URL и откройте через бота. Авторизация не отключается для разработки. BOT_POLLING=false разрешен для изолированных проверок API с тестовым токеном; этот режим не получает сообщения Telegram.

## Проверки

```bash
npm run lint
npm test
npm run build
python -m unittest discover -s bot/tests -v
```

Python-тесты используют отдельную временную БД и имитацию Telegram API, без отправки сообщений реальным пользователям. Они вызывают реальные обработчики создания рейса/посылки и отклика, затем проверяют видимость этих данных через HTTP API, статусы в обоих направлениях, блокировки, права и перенос старых сделок.

Проверка Python в контейнере:

```bash
docker compose build bot
docker compose run --rm --no-deps bot python -m unittest discover -s tests -v
```

## Хранение и резервные копии

Общая база в томе `bot_data`, путь `/app/data/crowdship.db`. Не выполняйте `docker compose down -v`: эта команда удаляет данные и настройки HTTPS.

```bash
docker compose exec bot python backup.py
```

Согласованная копия работающей SQLite появится в `./backups` на VPS. Настройте ежедневный запуск и перенос копий на другое хранилище. Обычное копирование только основного файла работающей SQLite может пропустить данные из WAL. Копии содержат пользовательские данные: ограничьте доступ.

Для восстановления остановите Python и веб-сервис, подставьте существующее имя копии:

```bash
docker compose stop app bot
docker compose run --rm --no-deps --user root --entrypoint sh bot -c 'rm -f /app/data/crowdship.db-wal /app/data/crowdship.db-shm && cp /app/backups/REPLACE_WITH_BACKUP.db /app/data/crowdship.db && chown app:app /app/data/crowdship.db'
docker compose up -d
```

Перед восстановлением сохраните текущую базу. Периодически проверяйте восстановление в отдельном окружении.

## Обновление и старые данные

Перед обновлением сделайте копию, затем выполните `docker compose up -d --build` и проверьте оба интерфейса.

Существующие Python-таблицы users, travel_trips и parcel_requests сохраняются. Новые таблицы добавляются при запуске. Старые match_deals переносятся в delivery_deals один раз; старые таблицы не удаляются. Дубли старых откликов объединяются по участникам и объявлению, некорректные сделки с самим собой пропускаются. Принятая старая сделка становится confirmed, завершенная — delivered. Подтверждение старого договора не считается подтверждением физического досмотра.

Если база Python уже существует, используйте именно ее: скопируйте согласованную копию в том bot_data под именем crowdship.db до первого рабочего запуска. Старый локальный путь `bot/crowdship.db` и новый `data/crowdship.db` различаются. Не удаляйте исходную базу. Экспериментальная Node-база app.sqlite из предыдущей промежуточной версии имеет другую схему и не подключается как база Python; ее данные требуют отдельного импорта, если вы успели ее использовать.

Backend также поддерживает PostgreSQL через DATABASE_URL. Для перехода потребуется изменить настройки сервиса bot в корневом Compose и добавить PostgreSQL. В этом случае делайте копии через pg_dump, SQLite-команда backup.py неприменима.

## Ограничения

Шаги незавершенных диалогов и введенные данные сохраняются в общей БД (таблица dialog_states) и восстанавливаются после перезапуска бота или контейнера. Сохраняются города, даты, категория, описание, ID фотографии и бюджет, если они уже введены. Пользователь продолжает с последнего сохраненного шага; /start и кнопка отмены очищают его черновик. Таблица создается автоматически при обновлении, входит в общую резервную копию и не требует Redis. Черновики, потерянные до этого обновления, восстановить нельзя. Уведомления о подборе и сделках сохраняются в очереди общей БД и повторяются при временных ошибках. Правила повторов и диагностика описаны ниже. Платежи, отзывы и проверка личности не реализованы. У новых пользователей нет выдуманных рейтингов. Лента ограничена последними 500 записями, список сделок в чате — последними 20. Ограничение записи API: 30 запросов в минуту на Telegram-пользователя, счетчик одного процесса.


## Очередь уведомлений

Таблица notification_jobs создается автоматически при обновлении и входит в резервную копию общей БД. При создании рейса/посылки или смене статуса сделки событие записывается в одной транзакции с основными данными. Фоновый обработчик Python-бота формирует и отправляет сообщения. Redis и отдельный контейнер не нужны.

- Временные ошибки сети, таймауты и ошибки сервера Telegram повторяются без ограничения числа попыток: пауза начинается примерно с 5 секунд и растет до часа. При ограничении Telegram учитывается retry_after.
- После перезапуска ожидающие записи продолжают обрабатываться. Задание, прерванное аварийной остановкой, освобождается по истечении аренды (до 120 секунд). Штатная остановка пытается освободить его сразу.
- Успешная доставка отмечается вместе с ID сообщения Telegram. Одинаковое событие и одно совпадение «посылка–рейс» не создают повторных записей. Текст и фотография доставляются отдельными заданиями: сбой фотографии не приводит к повтору текста.
- Заблокированный бот, недоступный чат или некорректный запрос Telegram переводят доставку в failed. Автоматические бессмысленные повторы прекращаются; после исправления запись можно вернуть в очередь вручную.
- Подсказки по уже закрытым или просроченным заявкам и уведомления заблокированным в сервисе пользователям отменяются (cancelled).
- Обработчик работает при BOT_POLLING=true; в тестовом API-only режиме очередь сохраняется, но сообщения не отправляются.

Проверить очередь и последние постоянные ошибки:

```bash
docker compose exec bot python notification_queue.py status
```

Повторить запись failed после исправления причины, подставив ее ID:

```bash
docker compose exec bot python notification_queue.py retry --id 123
```

Статусы pending/processing означают ожидание/обработку, sent — успешное выполнение, failed — постоянную ошибку, cancelled — отмененное неактуальное уведомление. В таблице хранятся как бизнес-события, так и отдельные доставки; sent для события означает, что задания отправки созданы.

Система гарантирует сохранение задания вместе с бизнес-данными и повторные попытки при временных ошибках, но не подтверждает прочтение. Если Telegram принял сообщение, а ответ потерялся или процесс остановился до записи результата в БД, повтор может доставить дубликат: у Telegram sendMessage нет ключа идемпотентности. Потерянные до внедрения очереди уведомления автоматически не восстанавливаются.

## CI в GitHub Actions

Workflow `.github/workflows/ci.yml` запускается при push, pull request и вручную через вкладку Actions → CI → Run workflow.

Проверки:

- Web checks: Node.js из .nvmrc, npm ci, проверка TypeScript, тест API-прокси, сборка фронтенда.
- Bot tests: Python 3.11, установка и совместимость зависимостей, интеграционные тесты общего API и бота, сохранения черновиков, очереди и повторов уведомлений.
- Docker integration: проверка локального и серверного Compose, сборка целей bot/web из одного Dockerfile, совместный запуск с тестовым токеном, проверка авторизации и создания заявки, общей БД, резервной копии и сохранности после перезапуска.

Настоящий BOT_TOKEN, .env, домен и GitHub Secrets для CI не нужны. В проверке контейнеров BOT_POLLING=false, отправка в Telegram выключена. Образы CI не публикуются. Отдельный workflow Deploy обновляет сервер только после успешного CI для main, если включен DEPLOY_ENABLED. Предыдущие проверки той же ветки отменяются при поступлении нового изменения.

После отправки файлов в GitHub откройте вкладку Actions. Для запрета слияния при ошибках настройте правила ветки main в GitHub и добавьте обязательные проверки Web checks, Bot tests и Docker integration.

Повторить контейнерную проверку локально:

```bash
docker build --target bot -t flyparcel-ci:bot .
docker build --target web -t flyparcel-ci:web .
python3 .github/scripts/container_smoke.py
```


## Автодеплой после CI

Workflow Deploy реагирует на успешный CI для push в main из этого же репозитория. PR, чужие репозитории, неуспешные проверки и устаревшие коммиты сервер не обновляют. Проверяется точный SHA прошедшего тесты коммита. Деплои выполняются по очереди и не отменяются посередине.

Для delivery используется сервер «Бегет боты», каталог `/opt/delivery` и домен `delivery.bantr.ru`. На сервере могут жить другие боты: у каждого отдельный Compose project, каталог, `.env`, том БД, очередь и имена образов. Только общий прокси `/opt/bots-edge` занимает порты 80/443. Приложения подключаются к внутренней сети bots-edge под отдельными именами, для этого проекта — delivery-app.

GitHub Repository Variables:

- DEPLOY_ENABLED=true — включает автоматическую отправку после CI.
- DEPLOY_HOST, DEPLOY_USER, DEPLOY_PORT — SSH-адрес и выделенный пользователь flydeploy.
- DEPLOY_HOST_FINGERPRINT — проверенный SHA256-отпечаток SSH-сервера; несовпадение прерывает подключение.
- DEPLOY_PATH=/opt/delivery, DEPLOY_PROJECT=delivery, DEPLOY_PROFILE=shared.

GitHub Secret DEPLOY_SSH_KEY содержит отдельный приватный ключ автодеплоя. Пароль сервера из Laret не передается GitHub. Токен Telegram и настройки приложения остаются только на сервере в `/opt/delivery/shared/.env` (права 600), не попадают в архив исходников и логи workflow. Публичная часть ключа установлена в authorized_keys пользователя flydeploy с запретом перенаправления портов и интерактивного терминала. Участие пользователя в группе docker дает административные возможности на сервере.

Порядок обновления:

1. GitHub отправляет архив ровно проверенного коммита по SSH с проверкой отпечатка.
2. Сервер блокирует параллельный запуск и распаковывает новую версию в releases/SHA.
3. Новые образы собираются до остановки старых контейнеров.
4. Если сервис уже работал, создается согласованная резервная копия SQLite.
5. Контейнеры обновляются с ожиданием healthcheck; проверяется публичный HTTPS API.
6. Только после успеха current переключается на новую версию.

При неудачном запуске выполняется попытка вернуть контейнеры предыдущей версии. База автоматически не откатывается: это могло бы удалить новые заявки. Поэтому изменения схемы должны сохранять совместимость с предыдущей версией. Историю релизов и резервные копии следует периодически проверять; автоматического удаления старых копий и образов пока нет.

Диагностика:

```bash
cd /opt/delivery/current
export COMPOSE_PROJECT_NAME=delivery
export FLYPARCEL_RELEASE=$(cat /opt/delivery/deployed-sha)
docker compose --project-name delivery --env-file /opt/delivery/shared/.env ps
docker compose --project-name delivery --env-file /opt/delivery/shared/.env logs --tail=100 bot app
docker compose --project-name bots-edge -f /opt/bots-edge/compose.yaml logs --tail=100 proxy
```

Чтобы добавить похожего бота, выберите другой DEPLOY_PROJECT, каталог и домен, отдельные токен и SSH-ключ, а также свободный WEB_PORT в его серверном .env. Общий HTTPS-прокси переиспользуется, второй экземпляр Caddy на 80/443 создавать не нужно.


## Мониторинг GlitchTip

Delivery подключается к monitoring.noscripts.ru через отдельные проекты delivery-backend (ошибки бота/API/обработчика очереди) и delivery-frontend (ошибки React Mini App). Проверки доступности Delivery API и Delivery Mini App выполняются раз в 60 секунд и проверяют HTTP 200 и ожидаемое содержимое.

В серверном `/opt/delivery/shared/.env` задаются GLITCHTIP_DSN, GLITCHTIP_FRONTEND_DSN и MONITORING_ENVIRONMENT=production. DSN — публичный ключ приема событий, не токен управления аккаунтом. Frontend получает свой DSN из публичного `/api/client-config`; это позволяет менять настройки без хранения секретов в Vite-переменных. RELEASE передается из SHA установленной версии.

Трассировка производительности и запись сессий выключены. В события не включаются тело запросов, заголовки, cookies, Telegram-профиль, breadcrumbs и локальные переменные. Токены ботов и Telegram initData дополнительно маскируются. Ожидаемые ошибки валидации API и обычная блокировка бота пользователем не создают ошибки в GlitchTip.

Без DSN мониторинг ошибок выключен. Недоступность GlitchTip не должна останавливать приложение или очередь. Uptime проверяет сайт и общую БД через health endpoint; системные метрики CPU/RAM и гарантии прочтения уведомлений этим не покрываются. Пока не настроена загрузка sourcemaps, JavaScript stack trace может содержать минифицированные имена.
